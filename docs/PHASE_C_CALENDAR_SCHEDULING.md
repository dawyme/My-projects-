### What is missing (Phase C scope per GAP_ANALYSIS.md)

1. Calendar views: **Day, 3-Day, Week, Month, Agenda** (+ technician/staff filtering), responsive/mobile.
2. Appointment API extension: `view=day|3day|week|month|agenda`, `date`, `serviceId`, `customerId`, `search`; events with end time/duration/work-order/recurring info.
3. Appointment create/edit/reschedule/cancel from the calendar UI.
4. **Server-side conflict validation** on booking create/update/assign: technician double-booking, overlapping appointments, approved time-off, working hours, breaks, closed days, invalid times.
5. Technician scheduling data: **WorkingHours, TimeOff, BreakPeriod, ClosedDay** models + admin APIs.
6. Service duration + buffers: `Booking.durationMin` override + `Booking.bufferMin` travel buffer; effective occupied time = `[start − buffer, start + duration]`.
7. Booking rules foundation (incremental, no rules engine): per-business `Setting` — min lead time, max booking window, strict working hours, conflict policy (warn/block).
8. Notifications **foundation**: clean server-side event bus (`booking.created/updated/rescheduled/assigned/cancelled`) so email/SMS/WhatsApp/Telegram channels (Phases G/H) can attach without redesigning appointments. Existing Resend calls stay byte-for-byte unchanged.
9. Recurring + dispatch compatibility: recurring occurrences (real bookings) must show on the calendar with a `recurring` flag; work-order linkage exposed on calendar events.

### Deliberate non-goals (stay in later phases)

- Multi-technician assignments (architecture = single `technicianId`; a join table is a Phase E decision).
- Online booking public flow (Phase D), notification engine/channels (G/H), customer portal (I), Google Calendar integration (L).
- No production DB writes; no auth changes; no changes to `pos-schema-v2.prisma` (known divergence, out of scope).

## 2. Design

### Schema (additive, non-destructive — SQLite + PostgreSQL compatible)

```prisma
model WorkingHours {  // per-technician weekly schedule (1=Mon … 7=Sun)
  id String @id @default(uuid()); businessId String; userId String
  day Int; start String; end String   // "HH:mm"
  @@unique([businessId, userId, day])
}
model TimeOff {       // technician time off / holidays
  id String @id @default(uuid()); businessId String; userId String
  startsAt DateTime; endsAt DateTime; reason String?
  status String @default("APPROVED")  // PENDING APPROVED REJECTED CANCELLED
  @@index([businessId, userId]) @@index([businessId, startsAt])
}
model BreakPeriod {   // daily break (business-wide when userId is null)
  id String @id @default(uuid()); businessId String; userId String?
  day Int; start String; end String
  @@index([businessId, day])
}
model ClosedDay {     // specific closed dates (holidays)
  id String @id @default(uuid()); businessId String
  date DateTime; reason String?
  @@unique([businessId, date])
}
// Booking gains: durationMin Int?  bufferMin Int?   (nullable → fully backward compatible)
```

New files: `backend/prisma/migrations/20260912000000_calendar_scheduling/migration.sql`.
Production applies via `prisma db push` at deploy time (NOT in this PR — no production DB writes).
CI applies the SQL file to SQLite. Existing rows need no backfill.

### Server-side validation (pure lib `backend/src/lib/scheduling-rules.js`)

- Effective duration: `Booking.durationMin ?? Service.durationMin ?? 60`.
- Occupied interval: `[start − bufferMin, start + durationMin]`.
- Checks: technician overlap (non-CANCELLED, same technician), approved time-off overlap,
  working hours (technician `WorkingHours` → business Settings `hours` → no constraint if
  neither exists), breaks, closed days, min lead time, max booking window.
- **Policy** (per-business `Setting` key `scheduling`, added as a Settings section):
  `{ conflictPolicy: "warn"|"block" (default "warn"), minLeadHours: 0, maxBookingDays: 0, strictWorkingHours: false }`.
  - `block` → conflicts (double-booking, approved time-off, lead/window) ⇒ 400 with conflict details.
  - `warn` (default) → 200/201 + `conflicts`/`warnings` in the response, surfaced in the UI.
  - `strictWorkingHours: true` promotes working-hours/break/closed-day violations to conflicts.
  - All defaults are no-ops ⇒ **zero behaviour change for existing flows/tests**; tenants opt in to strictness. (Hard-blocking by default would make the existing seeded `dispatch-reminders-contract` suite flaky — it restores a booking to a time that may exactly coincide with another seeded booking of the same technician.)
- Hard data validation (always 400): valid date, duration 5–1440 min, buffer 0–480 min.
  Past dates are deliberately allowed (dispatch boards reschedule and crews record past visits —
  see §3 deviation #1).

### API

- `GET /api/bookings/calendar?view=day|3day|week|month|agenda&date=YYYY-MM-DD&month=&technicianId=&status=&serviceId=&customerId=&search=` — backward compatible (`month` still works; `api.test.js` asserts `days` + `total`). Events add `end`, `durationMin`, `bufferMin`, `customerId`, `serviceId`, `technicianId`, `workOrder {id,reference,status}`, `recurring`. Gated by `requireFeature('calendar')` (feature already registered, default-enabled; SUPER_ADMIN always passes).
- `GET /api/bookings/availability?technicianId=&date=&time=&durationMin=&serviceId=&bufferMin=&ignoreBookingId=` — pre-flight check: `{ available, start, end, conflicts, warnings }`.
- `POST /api/bookings`, `PUT /api/bookings/:id`, `PATCH /api/bookings/:id/assign` — conflict validation (policy-sensitive), `durationMin`/`bufferMin` accepted, useful 400s with conflict list.
- New `backend/src/routes/scheduling.js` at `/api/scheduling` (mounted via `featureProtectedRoute('calendar')`, tenant-scoped, mutations `authorize('ADMIN','STAFF')` per codebase convention):
  `GET/PUT/DELETE /working-hours`, `GET/POST /time-off` + `PATCH/DELETE /time-off/:id`, `GET/PUT/DELETE /breaks`, `GET/POST/DELETE /closed-days`, `GET /technicians` (roster with hours + upcoming time-off).
- Settings: new `scheduling` section (DEFAULTS + zod schema + Settings page tab) — the only place booking rules live; no parallel rules engine.

### Notifications foundation

`booking.created`, `booking.updated`, `booking.rescheduled`, `booking.assigned`, `booking.cancelled`
(fire-and-forget, never throws, payload `{ bookingId, reference, businessId, actorId, actorName, details, warnings }`). Existing Resend email calls are **untouched** — the bus is additive so Phases G/H channels subscribe without redesign.

## 3. Implementation status (final)

All Phase C scope items are implemented and verified locally (offline sandbox, exact CI
sequence: `setup-prisma-offline → generate → migrate → seed → npm test`). The new migration
`20260912000000_calendar_scheduling` applies cleanly to SQLite (14 statements; PG-only FK
ALTERs are skipped by `migrate.js`, same as prior migrations).

### Deviations from the design above (all deliberate, found during verification)

1. **90-day past-date guard removed** from `validateAppointmentTimes`. The guard broke the
   pre-existing `dispatch-reminders-contract` suite (it reschedules the *oldest* seeded booking,
   which the seed places up to 360 days back) and would have blocked legitimate dispatch
   rescheduling / late visit recording. Past dates are now accepted; validation returns 400
   (not 500) for the remaining hard checks.
2. **`PUT /api/settings/:section` now merges over the previously stored value**
   (defaults → stored → body). Previously a partial body silently reset sibling fields to
   defaults, which made `strictWorkingHours` impossible to enable without re-sending
   `conflictPolicy`. Full-form saves (the admin UI) behave identically; existing suites that
   PUT partial bodies (`company`, `payment`) still pass — verified.
3. **Calendar event `workOrder` is `{id, status}`** (not `{id, reference, status}`): the
   `WorkOrder` model has no reference field; the UI links to `#/work-orders` instead.
4. **Zod `.refine()` schemas cannot be spread with `.shape`** (ZodEffects has no `shape`) —
   the working-hours/breaks schemas use a plain shape object + `requireStartBeforeEnd()`.
   The original draft silently dropped `start`/`end` from validated bodies; caught by the new
   contract suite before commit.
